01 · Capabilities

What it does

Pick a program, pick the instruction sets, press Run model. Everything runs locally inside the app: no server, no Docker, no account. The only network use is a check for a new version.

Programs

Three sources

Twelve built-in kernels (matmul, sieve, fir, pointer_chase and more, each with a size and seed), fourteen canned C programs, or your own C typed into the editor. Custom IR is there for controlling the instruction stream directly.

Real instruction sets

Your C, compiled in the app

The app carries clang and lld (LLVM 23.1.0) and llvm-mos, built to WebAssembly, plus each target's C library. Your program is compiled for all eight targets offline, in about a quarter of a second to two seconds per target, and run on the verified interpreters.

Model lowering

A second path, clearly labelled

Any program can also run on pseudo-backends that model how each architecture shapes code. A report is always all real or all lowered, and says which in its header.

Timing

Two deterministic models

A scoreboarded in-order pipeline (the default) and a detailed out-of-order model with renaming, a reorder buffer, load/store queues and speculation. Both produce model cycles, not nanoseconds.

Hardware

One profile, or presets

By default every target gets the identical core, caches and predictor, so differences come from the instruction streams. Illustrative per-target presets are available and ranked by modelled time instead.

Output

Reports you can keep

Ranked tables, instruction mix, a trace view and a protocol pane that names each target's library and oracle. Runs save locally and export to JSON and CSV.

One run, end to end

What happens between pressing Run and reading the table, for a program you wrote yourself.

The reference. Independently of the eight binaries, the program is compiled to the project's IR and run on a reference interpreter. That answer is the one every target must reproduce. The single stated exception: the 6502's int is 16 bits, so when an answer needs more it computes a different one, is shown, and is left out of every ranking because it did different work.

Counted

Exact, from execution

Instructions retired, instruction bytes executed, data-memory instructions (including implicit stack traffic such as an x86 call or a 6502 jsr), conditional branches and the share taken, distinct code executed, and platform traps such as SPARC window spills.

Modelled

From the shared core

Model cycles, cycles per instruction (shown, never ranked), branch mispredictions, I-cache and D-cache misses and memory line requests. Energy is deliberately not reported: the estimate is uncalibrated and cannot support a comparison.

03 · Worked example

One new program, eight machines

A program that is not in the corpus, typed into the packaged Windows app. It compiled for all eight targets, and every target printed the same output and returned the reference's answer, 1,241. The whole run took 2.6 to 4.6 seconds.

/* Insertion sort, a checksum and a histogram. Every
   intermediate stays below 32767, so a 16-bit int agrees. */
int data[48];

int main(void) {
  int seed = 123;
  for (int i = 0; i < 48; i++) {
    seed = (seed * 21 + 7) % 1009;
    data[i] = seed;
  }
  for (int i = 1; i < 48; i++) {
    int v = data[i], j = i - 1;
    while (j >= 0 && data[j] > v) {
      data[j + 1] = data[j]; j--;
    }
    data[j + 1] = v;
  }
  int buckets[4] = {0, 0, 0, 0};
  int check = 0;
  for (int i = 0; i < 48; i++) {
    buckets[data[i] / 253]++;
    check = (check * 7 + data[i]) % 4093;
  }
  printf("min=%d max=%d\n", data[0], data[47]);
  printf("buckets=%d %d %d %d\n", ...);
  return check;   /* 1241 on every target */
}

Reading it: AArch64 needed the fewest instructions and the fewest model cycles. SPARC retired half again as many instructions but nearly matched it on cycles. x86-64's variable-length encoding executed the fewest bytes. WebAssembly, a stack machine, retired more than twice as many instructions as AArch64 or x86-64. The 6502, with three 8-bit registers and no multiply, needed 6.4 times AArch64's instructions and 15 times its data-memory traffic. Counts include library code, and the libraries differ.

04 · How it was tested

Every claim has a reference

The interpreters are only as trustworthy as what they were compared against. Each tier below checks something the others cannot.

Lockstep6 targets

116 freestanding programs, including 12 randomly generated per target, run on the interpreter and on the reference together. Every register is compared before every instruction: 283,652 instructions in all, against qemu for five targets and against the physical x86 processor for x86-64. Then the final memory and register state is compared byte for byte.

Decodeby signature

Every instruction in every fixture is decoded by the project and by llvm-objdump, and the two must agree on what every instruction is. This audit found real encoding mistakes that execution alone had not, including four in the POWER decoder.

Whole programslibc tier

18 programs per target, linked against a real C library, must print the same bytes and exit the same way as under the reference. This covers system calls, printf and the start-up code.

WebAssemblyno stepping possible

Engines compile WebAssembly, so there is nothing to single-step. Instead every operation is compared against a real engine on every edge value of its operand types (both zeros, both infinities, both signs of NaN), then 14 whole modules are compared on all of linear memory against wasmtime.

6502per-opcode vectors

23,502 single-instruction cases from the SingleStepTests project cover every documented opcode from arbitrary states, including decimal mode. They are generated by a reference implementation built to the published documentation and test sets, not recorded from silicon. Whole programs are compared against mos-sim, which gets decimal-mode N and V wrong. The vectors and Bruce Clark's documented NMOS behaviour agree on that, and the app follows them.

In-app compilerbyte identity

The compiler inside the app rebuilds all fourteen shipped programs, and for the five musl targets and the 6502 the result must be the shipped binary, byte for byte. SPARC and WebAssembly link differently by design and are held to the reference's answers.

Timing modelimpossibility checks

A test runs the timing model over all eight targets and checks for what a trace bug makes impossible: a predictor that never mispredicts, returns that never pair with calls, memory counted by class exceeding memory seen in the trace.

The packaged append to end

Before release, the packaged Windows app was launched and driven through its real window over the DevTools protocol: select Custom C, paste the program above, run all eight targets, read the report. Done by hand for each packaged build here, not yet in CI.

05 · What testing caught

Bugs found on the way

Each of these produced plausible numbers until a check was added that could see it. All are fixed.

MIPS branchesThe outcome was recorded on the delay slot instead of the branch, so every branch looked untaken: 0% mispredicted on every program.
SPARC returnsret, retl and indirect calls are all jmpl and were all timed as indirect jumps, so no return was ever predicted. Register-window spills and fills moved 64 bytes each for free.
POWER conditional returnsA beqlr that fell through still popped the return stack, and every later return mispredicted.
x86 string movesA rep movsq reported its first element instead of the range, so copying a page cost one store.
In-app clangThe WebAssembly port of LLVM returned a stale error code from every file close, so clang reported every object it wrote as an I/O failure.
Version stringsA build from the source tarball left the release commit out of each ELF's .comment, the only difference from the shipped binaries.
6502 fixturesThe committed 6502 binaries could not be rebuilt from the repository. Every one differed while every output agreed. They were regenerated from the pinned SDK.
Host-dependent fixturesqemu's stack address depended on the host kernel, and x86 recorded whichever values the capturing CPU left in undefined flags. Both are now fixed at capture, and two machines produce identical fixtures.
The Windows iconA build setting meant the executables had never carried the app's icon.
06 · Delivery

From commit to installer, without a hand step

Two workflows on GitHub carry every change through. Everything generated is reproducible from the repository and pinned by checksum.

When a generator changes

Regenerate

  • Rebuilds only the Docker images whose inputs changed. Each is stored under a hash of its inputs, so an unchanged one is a pull.
  • Recaptures every target's fixtures and rebuilds the in-app compiler.
  • Runs the regular and deep suites on the result.
  • Publishes a new compiler bundle and commits what changed.
Every push and pull request

CI

  • Fetches the compiler bundle and verifies it against the lock file.
  • Typecheck, lint, tests, build.
  • The deep suite.
Main, or a v* tag

Release

  • Packages Windows, Linux and macOS, each on its own runner.
  • Main refreshes the rolling Latest main prerelease.
  • A tag such as v1.1.0 publishes that version.
  • Dependabot proposes updates weekly, as pull requests CI checks.
07 · Limits

What it does not claim

  • No measured hardware performance. Cycles are the model's, on one idealised core. Nothing in the app is timed on real silicon.
  • The instructions are real; the timing is not. Instruction counts, bytes and memory traffic are exact. Cycles, cache misses and mispredictions are modelled.
  • Libraries differ. Most targets link musl, SPARC links picolibc, WebAssembly links wasi-libc and the 6502 links llvm-mos's own, so a difference inside printf is partly a difference of library.
  • Your C is a subset. Programs must be valid Guest C: signed int, char, double, pointers, arrays and structs; no unsigned, long or float.
  • The 6502 is small. It has 64 KiB and a 16-bit int. One corpus program does not fit, and it computes different answers when a result needs more than 16 bits. The report says so.
  • Updates. Installed copies update from numbered releases only. The Windows installer and the Linux AppImage update themselves after asking to restart; macOS, the portable exe and the tarball say a new version is out and link here.
  • Unsigned builds. Windows shows a SmartScreen prompt and macOS needs right-click, Open, the first time. The CI macOS build is Apple Silicon only.
